# Review, August 2026 — third round, against the v2.6 architecture

> Scope: the whole application at `v2.6.0` (`src/`, `test/`, `migrations/`, all `*.md`).
> Method: category sweeps (the technique that
> [round 2 of the July audit](./AUDIT-2026-07.md) established), plus one new technique —
> **cross-reading code comments against the ledgers they claim to be recorded in.**
>
> The headline finding is not a new class of bug. It is that
> **July's round-2 sweep of "every anonymous path that writes to D1" found the endpoint
> that writes 0.1 rows per request and missed the middleware that writes 1 row per
> request** — and the middleware runs on requests the endpoint never sees.

## Why a third round, and why now

Two things changed since July that invalidate parts of the previous review's conclusions,
so re-reading was not optional:

1. **A new trust boundary exists.** v2.6 moved the streaming transform into a Durable
   Object ([ADR-0015](./adr/0015-durable-object-streaming.md)). The
   [threat model](./THREAT-MODEL.md) was written at v2.0.0 and has no section for it.
2. **Numbers moved.** The image budget went 1.5 MB → 16 MB, per-message images 4 → 10,
   single attachments 1400 KB → 5 MB. Every prose statement derived from the old numbers
   silently became wrong, and only some of them were updated.

The new technique is worth naming because it produced two findings on its own. Code
comments in this repo routinely say *"recorded in DEBT"* or *"this is the only place
that…"*. Those are **assertions about other files**, and nothing checks them. Reading a
comment and then going to verify the claim it makes is a cheap sweep with a high hit rate,
because the claim was true when written and nobody re-checks it afterwards.

## F1 · `visits` is a second anonymous D1 write path, and a weaker one than the hardened one 🔴

**Verdict: defect (availability), not currently exploited. ✅ Fixed in v2.6.1** — the analysis
below is kept as written; the fix is described at the end of this section.

`src/routes/api/csp-report.ts:4` opens with:

> 這是全站**唯一**的匿名 D1 寫入口，所以防線比其他端點厚
> *(this is the site's only anonymous D1 write entry point, so its defences are thicker)*

That statement is false, and the counter-example runs **before** the router on every single
request: `src/router.ts:107` calls `visitLog()`, which writes one `visits` row
(`src/routes/_middleware.ts:35-65`).

Compare the two paths in the same terms:

| | `/api/csp-report` | `visitLog` |
|---|---|---|
| reachable anonymously | yes | yes |
| sampling | **10 %** | none |
| per-IP rate limit | **5/min, 50/day (DO)** | none |
| behaviour when the limiter is down | **fails closed — does not write** | n/a |
| rows written per qualifying request | 0.1 | **1** |
| triggered by | a browser CSP violation | any request with `Accept: text/html` |

The last row is the one that matters. `shouldLog` (`_middleware.ts:27-32`) returns true on
the **first** disjunct:

```js
return (
  accept.indexOf("text/html") >= 0 ||   // ← any path, including ones that don't exist
  PAGE_PATHS[p] === 1 || …
);
```

So `GET /does-not-exist-9f2a` with `Accept: text/html` writes a row, returns the SPA shell
with `200`, and — because every path is distinct — defeats edge caching on the way in.
Only `/logs`, `/admin`, `/api*`, `/img/*`, `/auth*`, `/relay/*` and `/vpn/sub*` are excluded.

### Why this is worse than "someone could spam the log table"

Cloudflare's free tiers are **100,000 Worker requests/day** and
**100,000 D1 rows written/day** ([D1 pricing][d1p]). Those two numbers are identical, and
visit logging consumes them **1:1**. The consequence is structural rather than adversarial:

> The cheapest, least valuable write on the site has first claim on the same budget as
> every write that matters, and nothing reserves headroom for the second group.

One playground turn writes roughly four rows (`pg_messages` ×2, the `pg_conversations`
update, `req_log`). A login writes two. Under a crawl — or a modest traffic spike, or one
badly-behaved scraper — the visit log can reach the daily cap on its own, and then
**D1 stops answering queries entirely**, not just writes:

> "When your account hits the daily read and/or write limits, you will not be able to run
> queries against D1. D1 API will return errors to your client." — [D1 pricing][d1p]

At that point the site's own instrumentation cannot tell anyone:

- `errlog` is a D1 table, so the error about D1 cannot be recorded;
- `tgAlertScan` (`src/cron.ts:39-69`) reads `errlog` **from D1** to decide what to alert on;
- `runJob` records outcomes into `settings` — also D1.

**The alerting system depends on the subsystem whose failure it would need to report.** The
site keeps serving pages (fail-open is deliberate and correct everywhere else), so the
symptom is: logins silently fail, chats silently fail to persist, and no alert fires.

### This was known and did not reach the ledger

`src/cron.ts:274-278` names the risk precisely — daily 100k writes, crawler bursts, whole-site
write failure — and closes with *"（那需要取樣或寫入上限，記在 DEBT）"*, "that needs sampling
or a write cap, recorded in DEBT". It was not recorded in DEBT. `DEBT.md` #18 covers
`visits`/`errlog` only as **table growth**, with the threshold "either table passes 500,000
rows" — a storage concern, on a different time constant, already partly answered by the
180-day retention added on 2026-07-29 (`RETAIN.visits`). The one-day burst has no entry, no
threshold, and no owner.

### Fix, cheapest first

1. **Stop logging paths that don't exist.** Move `visitLog` to run *after* a route match, or
   drop the bare `Accept: text/html` disjunct so only known page shapes qualify. This alone
   removes the unbounded-cardinality case and costs nothing.
2. **Sample, exactly as `csp-report` already does.** `visits` is an analytics table; 1-in-N
   with a stored multiplier keeps the trend and divides the cost by N.
3. **Reserve headroom.** A daily counter in `settings` (or a `visit` namespace on the
   existing `RateLimiter` DO — `RateCheckArg.svc` already exists for exactly this kind of
   split) that stops *logging* at, say, 40,000 rows/day leaves 60 % of the budget for writes
   that carry user data.
4. **Make the failure sayable.** `/api/health` should surface "D1 write quota exceeded" as a
   distinct state, since the normal alert channel provably cannot.

(1) and (3) are each a few lines and preserve the existing behaviour for real visitors.

### Fixed — v2.6.1, 2026-08-06

(1), (3) and (4) shipped; (2) was not needed once (1) removed the unbounded-cardinality case.

- **L1 allowlist**: `shouldLog` now matches a fixed page list plus two path patterns. Scanner
  traffic writes nothing. The "log known pages even without `Accept`" behaviour is preserved
  deliberately — that was there to catch bots on real pages, and it still does.
- **L2 daily cap**: `VISIT_GUARD` — 40,000 rows/day (40 % of the free-tier write budget),
  counted in the existing `RateLimiter` DO under `visit:global`, consulted on a **1-in-20
  sample** with the verdict cached per isolate until the next UTC day. Normal traffic costs
  about six DO calls a day; a flood converges within one sampling interval and then costs
  nothing. Denial and limiter failure both stop logging — deliberately the inverse of
  `lib/quota.ts`, on the same reasoning that makes `csp-report` fail-closed.
- **Leading-indicator alerting**: tripping the cap writes one `visits.cap` row to `errlog`,
  which the existing five-minute `tgAlertScan` pushes to Telegram **while D1 is still healthy**.
  This is the actual answer to the finding — the alert cannot depend on the failure it reports,
  so it fires on the self-imposed cap 60 % below the platform limit instead.
- **`/api/health` classifies D1 errors** (`db_error`: `quota` / `error` / `unbound`). It needs
  no D1 write to answer, so it stays available in exactly the situation the rest of the
  observability stack does not.

Tests: `test/int/middleware.test.ts` (allowlist, sample-to-cap arithmetic, deny **and** throw
both stopping, per-day reset, no DO calls after stopping, site response unaffected) and
`test/int/smoke.test.ts` (error classification, and that raw messages never leak).

The residual, stated rather than hidden: the cap is **approximate** (±1 sampling interval), and
`stopped` is per-isolate, so each live isolate writes its own `visits.cap` row on the day it
trips. Both are acceptable for a guard rail — bounded, and a duplicated alert beats a missing
one.

## F2 · The client-side sanitizer allows `style` on model-generated HTML 🟠

**Verdict: defect (UI redress / phishing surface), low exploitation cost, high blast radius
inside an authenticated page.**

Two sanitizers guard two different content paths, and they are built on opposite principles:

| | `src/lib/sanitize.ts` (server, admin markdown) | `playgroundpage.ts:293-306` (client, model output) |
|---|---|---|
| principle | **whitelist** — unknown tags and attributes are dropped | **blacklist** — 9 tags and `on*` are removed |
| `style` attribute | dropped (`ATTR_GLOBAL` is `class`/`title` only) | **kept** |
| `<svg>` | dropped with contents | kept |

Model output is attacker-influenceable: prompt injection through a pasted document, a web
page a member quotes, or a compromised upstream all end in `md.innerHTML = mdRender(content)`
(`playgroundpage.ts:942`). With `style` surviving and CSP running
`style-src 'self' 'unsafe-inline'` (DEBT #9), a reply can render a full-viewport fixed
overlay inside the real, logged-in origin:

```html
<div style="position:fixed;inset:0;z-index:9999;background:#0b0b0b">
  … "Your session expired — sign in again" …
  <a href="https://attacker.example/google">Continue with Google</a>
</div>
```

No script executes, so CSP is not violated. The `<a>` is even given
`target="_blank" rel="noopener noreferrer"` by the sanitizer itself
(`playgroundpage.ts:304`). What makes this worth fixing rather than accepting is that the
page it hijacks is the one where the member normally *does* see Google sign-in prompts.

**Fix**: add `STYLE` handling to the attribute loop — `if (nm === "style") { n.removeAttribute(a.name); continue; }`
— one line, and it brings the client path in line with the server path. Consider also
dropping `<svg>`/`<math>` to match `DROP_CONTENT`.

**Documentation note**: THREAT-MODEL §2.7 currently reads "a DOM sanitizer (script/style/iframe
stripped…)". That is true of the `<style>` *element* and false of the `style` *attribute*, and
the sentence reads as covering both.

## F3 · The tag blacklist's uppercase assumption does not hold for SVG content ⚪

**Verdict: latent defect. Not exploitable in the current code; the reasoning that makes it
safe is not the reasoning the code relies on.**

`playgroundpage.ts:294` keys its blacklist on `n.tagName` with uppercase literals
(`{SCRIPT:1, STYLE:1, …}`). Per DOM, `tagName` is uppercased **only for elements in the HTML
namespace**. Inside `<svg>`, elements are in the SVG namespace and `tagName` returns the local
name as parsed — so `<svg><script>` yields `"script"`, and `BAD["script"]` is `undefined`.
The element survives the sanitizer.

It does not execute, for two independent reasons: scripts inserted via `innerHTML` never run,
and CSP has no `unsafe-inline`. So there is nothing to fix today. It is recorded because the
blacklist is *believed* to remove script elements and does not, and the belief is what a
future change would rely on — a move to a context that parses-and-executes, or a
`setHTMLUnsafe` refactor, would make it live with no visible edit to this function.

**Fix**: compare `n.tagName.toUpperCase()`, or better, switch this function to a whitelist so
it matches the server-side sanitizer's principle rather than its list.

## F4 · Four prose statements that the code has since contradicted 🟠

**Verdict: documentation defects. Grouped because the pattern matters more than any one of
them.**

| # | Claim | Where | Reality |
|---|---|---|---|
| a | images sent upstream still capped at **1.5 MB** | `README.md:247-249`, `README.zh-TW.md:220`, `ADR-0013:102-103` | `PG_LIMITS.maxImgBytesTotal` is **16,000,000** (`playground.ts:44`), ceiling 32 MB, admin-tunable via `pg_img_total_kb`. `API.md:310` and `:563` are correct — the two READMEs are not |
| b | "中斷連線（前端按「停止」）＝停止生成" | `API.md:515` | The opposite is the headline feature of [ADR-0012](./adr/0012-finish-reply-after-disconnect.md): generation **continues** for `BG.budgetMs` (20 s) after disconnect, checkpointing every 3 s, and DEBT #15 records that "stop" cannot be distinguished from "closed the tab" |
| c | "站上自己的 maxImgPerMsg（4）與 maxImgBytesTotal（1.5MB）" | `modelcaps.ts:24-25` | 10 and 16 MB. The comment's *argument* is still correct; only its numbers are stale |
| d | "全站**唯一**的匿名 D1 寫入口" | `csp-report.ts:4` | See F1 |

This repo already treats documentation drift as a build failure — `tools/check-docs.mjs`
fails CI when a test count, an E2E count, a version string or the COMPARISON architecture
rows disagree with reality, and its own header explains why the first version of that check
was wrong. All four items above sit in the class it does not yet cover: **numbers that exist
in code as constants and in prose as claims.**

**Fixed — v2.6.1.** All four prose items corrected, and (a)'s *class* is now enforced by
`check-docs.mjs`, which reads `maxImgBytesTotal` / `maxImgBytesCeiling` / `maxImgPerMsg` out of
`src/lib/playground.ts`. Two design choices in that check are worth more than the check itself:

- **It anchors on the constant's name, not on the number.** That establishes a convention —
  *if you quote a constant's value in prose, name the constant* — and the convention is what
  makes precise checking possible. Matching on "16MB" instead would have to guess which
  occurrences refer to this constant, would misfire, would acquire an exemption list, and would
  then be worthless. The cost is an honest coverage gap: **numbers quoted without the constant
  name are not checked.** That gap points the incentive the right way.
- **Dated records are excluded** (`docs/adr/**`, the audit and review documents). ADR-0013's
  "1.5 MB" was true on the day it was written and is annotated with an addendum instead.
  A checker that forces people to rewrite dated records is worse than a stale number.

Verified by deliberately breaking each constant and confirming the build goes red.

## F5 · The DO trust boundary is undocumented ⚪

**Verdict: no defect found. Documentation gap.**

`PgStream.fetch()` (`src/do/pg-stream.ts:57-98`) accepts an envelope carrying `userId`,
`isAdm`, `convId`, `demo`, `demoMaxTokens` and the **entire channel row including
`ch.api_key`**, and re-derives nothing. Every authorization decision was made in the Worker
before the handoff (`chat.ts:46-234`).

This is correct: a Durable Object namespace is reachable only through a binding, so the only
possible caller is this Worker. But that is an *inherited platform property*, and the July
threat model — written before the DO existed — never states it. Two consequences worth
writing down rather than leaving implicit:

- The security review of the playground now lives **entirely** in `chat.ts`. Anyone adding a
  second caller of `PG_STREAM`, or moving a check "down into the DO for symmetry", moves a
  boundary the docs don't mark.
- `job.isAdm` decides whether upstream error text is shown verbatim (`pgchat.ts:213-217`).
  It is a privilege claim travelling in a message body — safe today for the reason above,
  and worth knowing that it is a claim rather than a lookup.

**Fix**: a §2.7c in the threat model. Done in this pass.

## Checked and found sound

Negative results are part of the report; without them "we looked" is unfalsifiable.

- **SQL injection** — every interpolation into a statement was traced. All are either module
  constants (`cron.ts:131` table names), or integers already through `parseInt` with a range
  check (`logs.ts:24-25`, `articles/index.ts:13-17`, `pages.ts`, `errors.ts`), or arrays whose
  elements passed `parseInt(...)` + `> 0` before `.join(",")` (`chat.ts:200`,
  `playground.ts:375`, `filestore.ts:326`/`:357`, `cron.ts:297-302`). `users/[id].ts:153`
  builds `SET` from a fixed field list, never from request keys. No finding.
- **IDOR** — every `:id` route re-derives ownership in the query rather than checking after
  the read (`conversations/[id].ts:12-18`, `files/[id].ts:57`, `chat.ts:165-168`,
  `vpn/sub/[token].ts:98`). Not-yours returns 404, not 403. No finding.
- **OAuth** — `state` is bound to an HttpOnly, `Path=/auth`, 10-minute cookie and compared
  before the code exchange; `aud` is checked; the id_token comes from Google's token endpoint
  over TLS so signature verification is genuinely unnecessary; `safeNext` blocks both `//` and
  `/\` (the July finding). `iss`/`exp` remain unchecked — already DEBT #27, correctly
  classified there as defence-in-depth rather than a hole.
- **Secret leakage into responses** — `/api/relay/channels` and `/api/playground/models`
  select explicit column lists that exclude `api_key` and `base_url`; `redactSecrets`
  (`observe.ts:25-37`) is applied at the observability layer rather than at each of its twelve
  call sites, which is the right place for it. No finding.
- **`fastsse` fast/slow path equivalence** — the `"error"` / `"usage":{` bail-outs are correct,
  `FIELD_RE` cannot match inside a JSON string value (an unescaped `"` cannot appear there),
  and `n` is in `PROTECTED_BODY_KEYS` precisely because it would desynchronise the two paths.
  Tests pin the equivalence. No finding.
- **Quota atomicity** — `RateLimiter.check()` still contains no `await`, which is the whole
  of ADR-0007's argument; the sliding-window arithmetic and the lazy day-key reset are sound.
  No finding.
- **`sanitize.ts`** — swept for the usual whitelist bypasses (entity-encoded schemes, control
  characters inside URLs, attribute-quote confusion, `hasOwnProperty` on the tag map,
  self-closing dangerous containers). It holds. This is a better sanitizer than most
  dependencies people install to avoid writing one.

## Assessment

Things this codebase does that most production systems — not just most side projects — do
not:

- **Decisions are recorded with their reversal conditions.** DEBT entries carry a threshold,
  not a vague intention. ADR-0014 is kept in the tree *after being wrong* and labelled as such.
  That is the single strongest signal in the repository.
- **Claims are wired to CI where they can be.** Test counts, E2E counts, version strings, CSP
  hashes, OpenAPI ↔ route-table equality. The check-docs header explains why its own first
  implementation was wrong (counting `it(` statically under-reports loop-generated tests) —
  a corrected measurement documented as a correction.
- **Measurement precedes optimisation, and negative results survive.** The `new TransformStream()`
  arm that measured *worse than doing nothing* is in the README. The local bench's ~95×
  under-report is stated next to the numbers it produced.
- **Failure direction is a design parameter.** Member quotas fail open, anonymous demo fails
  closed, CSP reporting fails closed — same Durable Object, opposite policies, the policy
  living in the caller.

What separates this from the next level up is narrower than it looks, and F1 names it: the
project is excellent at reasoning about **the failure modes it has already thought about**,
and has no mechanism for the ones it has not. The alert channel cannot report the failure of
the database it lives in. The debt ledger is maintained by hand, so a comment saying
"recorded in DEBT" is trusted rather than verified. Both are the same shape — a claim with no
independent checker — and this repository is already unusually good at building independent
checkers. Pointing three more of them at itself is a smaller change than anything in v2.6 was.

**中文摘要**

2026-08 第三輪稽核，對象是 v2.6.0。方法沿用 7 月第二輪確立的「逐類別橫掃」，另外加一招新的：
**把程式註解裡對別的檔案下的斷言，一條一條回去查證**。註解常寫「記在 DEBT」「這是全站唯一的…」，
那些是**對其他檔案的主張**，而沒有任何東西在檢查它們——寫的當下是真的，之後沒人回頭看。
這一招自己就抓到兩條。

**F1（🔴 可用性）`visits` 是第二個匿名 D1 寫入口，而且比被加固的那個更弱。**
`csp-report.ts:4` 開頭寫著「這是全站**唯一**的匿名 D1 寫入口」——這句話是錯的，而反例
跑在**每一個請求的最前面**：`router.ts:107` 的 `visitLog`。兩者對比：csp-report 有 10% 取樣、
每 IP 5/分 50/日 的 DO 限流、限流器壞掉就不寫；`visitLog` 三樣都沒有，而且
`Accept: text/html` 就足以命中（`_middleware.ts:27-32` 的第一個 `||`），**連不存在的路徑都算**，
每個路徑還都不一樣、順便讓邊緣快取失效。

真正的重點不是「有人可以灌爆日誌表」，而是**兩條免費額度是 1:1 的**：Workers 每日 10 萬請求、
D1 每日 10 萬列寫入，而瀏覽紀錄用掉的正好是一對一。也就是說——
**全站最便宜、最沒價值的那筆寫入，跟所有有價值的寫入共用同一個預算，而且優先權在前面，
沒有任何機制替後者保留空間。**一次聊天約寫 4 列、一次登入寫 2 列；被爬蟲密集掃的那天，
瀏覽紀錄自己就能把額度用完，然後 D1 **連查詢都會開始失敗**（不只寫入，見 Cloudflare 官方說明）。

而那一刻站台講不出話來：`errlog` 是 D1 的表、`tgAlertScan` 要從 D1 讀 errlog 才知道要告警什麼、
cron 的執行結果也寫回 D1 的 settings。**告警系統依賴的正是那個一旦故障、它就必須回報的子系統。**
頁面照樣能開（fail-open 在別處都是對的），所以症狀是：登入靜靜地失敗、聊天靜靜地存不進去、
沒有任何告警。

更值得記的是：`cron.ts:274-278` **已經把這個風險寫得很精確**，結尾說「記在 DEBT」——
但它沒有進 DEBT。DEBT #18 只管「表破 50 萬列」的空間成長，那是完全不同的時間尺度，
而且 07-29 加的 180 天保留期已經處理掉一半。單日暴衝這條沒有條目、沒有門檻、沒有負責人。
修法由便宜到貴：① 不要記不存在的路徑 ② 比照 csp-report 取樣 ③ 用既有的 RateLimiter DO
（`RateCheckArg.svc` 本來就是為這種切分存在的）留 60% 額度給有價值的寫入
④ `/api/health` 要能把「D1 額度爆了」講出來，因為正常的告警管道證明講不出來。

**F2（🟠）客戶端消毒器放行 `style` 屬性。** 站上有兩個消毒器、原理相反：伺服器端
（`sanitize.ts`）是**白名單**，`style` 進不來；客戶端（`playgroundpage.ts:293-306`）是
**黑名單**，只擋 9 個標籤與 `on*`，`style` 原封通過。模型輸出是可被影響的（提示注入、
貼進來的文件、被打下來的上游），最後進 `md.innerHTML`。配上 CSP 的
`style-src 'unsafe-inline'`（DEBT #9），一則回覆就能在**真正的登入中網域**上蓋一張滿版
固定定位的假登入畫面——沒有任何 script 執行，所以 CSP 不會擋，而那個 `<a>` 還會被消毒器
自己加上 `target="_blank"`。修法一行：屬性迴圈裡把 `style` 一併移除。
順帶：威脅模型 §2.7 寫「script/style/iframe stripped」，那是 `<style>` **元素**成立、
`style` **屬性**不成立，而那句話讀起來像兩者都涵蓋。

**F3（⚪ 潛伏）黑名單的大寫假設對 SVG 不成立。** `BAD` 用大寫鍵比對 `n.tagName`，但依 DOM 規範
`tagName` **只對 HTML 命名空間**的元素大寫；`<svg><script>` 拿到的是小寫 `"script"`，
`BAD["script"]` 是 undefined，元素活下來。今天不會執行（innerHTML 插入的 script 本來就不執行、
CSP 也沒有 unsafe-inline），所以現在沒有洞。記下來是因為**這個函式被相信會移除 script，而它並沒有**，
哪天輸出被搬到會解析並執行的環境（或改用 `setHTMLUnsafe`），這個假設就會在沒有任何可見改動的
情況下失效。

**F4（🟠 文件）四句已被程式碼推翻的敘述**：(a) 兩份 README 與 ADR-0013 還寫「送上游的圖片仍上限
1.5MB」，實際是 16MB（`playground.ts:44`；API.md 是對的）；(b) `API.md:515` 寫「中斷連線＝停止生成」，
與 ADR-0012 的主打功能**正好相反**（斷線後續跑 20 秒、每 3 秒存檔）；(c) `modelcaps.ts:24-25`
的註解還寫 4 張／1.5MB；(d) 就是 F1 那句。這四條的共同點是：這個 repo **已經**把文件漂移當成
建置失敗（`check-docs.mjs` 管測試數、E2E 數、版本號、對照表架構列），而這四條落在它還沒涵蓋的
那一類——**同時以常數存在於程式、以主張存在於散文的數字**。建議把 `PG_LIMITS` 也納入檢查，
(a) 這類就再也不會復發。

**F5（⚪ 文件缺口）DO 的信任邊界沒有被寫下來。** `PgStream.fetch()` 全盤信任交棒信封
（`userId`／`isAdm`／整列渠道含 `api_key`），一項都不重新推導。**這是對的**——DO 命名空間只能
透過綁定觸達，唯一可能的呼叫端就是自家 Worker。但那是**繼承自平台的性質**，7 月的威脅模型
（寫在 DO 出現之前）從沒把它寫出來。兩個值得明講的後果：playground 的安全審查現在**完全**
住在 `chat.ts` 裡；而 `job.isAdm` 決定會員看不看得到上游錯誤原文，它是一個**在訊息本體裡旅行的
權限主張**而不是一次查詢。本輪已補上威脅模型 §2.7c。

**F6／F7（⚪ 舊案重申）**：relay 仍未拒收 `.`／`..`（DEBT #22，修法是一個 `.filter()`）；
`/relay` 仍然沒有 E2E（7 月誠實揭露、至今仍在，第六條 E2E 是數學渲染回歸，不是 relay）。
重申的理由是不讓「當時決定先不修」默默熟成為「沒有人記得決定過」。

**查過而確認沒問題的**（負面結果也是報告的一部分，否則「我看過了」無法被證偽）：
所有 SQL 字串拼接（全是模組常數或已 `parseInt` 驗過的整數／整數陣列）、所有 `:id` 路由的歸屬
檢查（一律寫進 WHERE 而不是查完再比，且回 404 不回 403）、OAuth 全流程、回應中的機密欄位、
`fastsse` 快慢兩路徑的等價性、限流 DO 的原子性、以及 `sanitize.ts` 本身——那支消毒器
比多數人為了不自己寫而安裝的套件都嚴謹。

**總評**：這個專案真正稀有的地方不是功能，是**決策都帶著反轉條件**（DEBT 每條都有門檻、
ADR-0014 錯了還留在樹裡並標明錯在哪）、**能自動檢查的主張都接上了 CI**、**量測先於最佳化
且負面結果會留下**（`new TransformStream()` 那條比不改更糟的數據就寫在 README 裡）、
**失敗方向是一個設計參數**（同一顆 DO，會員 fail-open、匿名 fail-closed）。
與「再上一級」之間的差距比看起來窄，而 F1 正好指出它是什麼：這個專案**對已經想過的失敗模式
推理得極好，但對還沒想過的那些沒有機制**。告警管道無法回報它所寄生的資料庫的故障；債務帳本
靠手維護，所以一句「記在 DEBT」是被信任而不是被驗證的。這兩件事是**同一個形狀**——
一個沒有獨立檢查者的主張——而這個 repo 恰恰非常擅長建獨立檢查者。把其中三個轉過來對準自己，
比 v2.6 做的任何一件事都小。
